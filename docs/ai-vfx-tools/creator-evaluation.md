# 每个创作闭环的独立测评

这是用户在 2026-11-05 明确要求的持续开发方式，适用于后续每个已可用功能闭环。完成顺序是：公开契约与实现、技术验证、独立复杂创作、问题修复、公开接口补测和证据归档。开发者自己的示例不能替代独立创作者。

## 独立性与任务

每轮使用不继承实现对话的子 agent，并固定隔离副本与源码摘要。它可以读取 tools 返回的公开定义、SDK 文档、效果参考源码，通过普通编辑器写自己的作品；不能读工具/SDK实现、实现测试、冻结 sources.json 或其他创作者答案。记录实际读过的资料。允许作者按正常产品契约写代码，不能用“写了代码”判工具失败。

任务应需要当下功能，并容纳原创结构、非粒子主体、材质与运动组合，不能只是改预设颜色。作者先写用途、尺度、意图与问题，实际观察初稿，再至少完成两类有意义的局部修改；使用适合问题的事件或绝对时间窗口，验证并从同一个选定 run 导出。历史/复现功能用真实改稿后复查检验。

## 三个判断维度

| 维度 | 必须说明的证据 | 不成立的替代判据 |
| --- | --- | --- |
| 创意表达与帮助 | 哪种原创轮廓/运动/材质可表达或受阻，哪项能力具体促成它；保留原尺寸及弱光等相关对照 | 作品运行成功就等于艺术达成；一段代码较短就等于表达更自由 |
| 使用负担 | 原始失败、恢复提示、实际往返；哪些采样/求解/扫描/观察算法仍被重复实现，哪些是艺术设计工作 | 传递 run ID、正常编辑、做艺术取舍都是工具负担；需要 GUI 才算工具台 |
| 能力提升 | 指出引导/复用/算子让哪一部分从难实现变得可组合，并用实际作品与局改证明；对未做的匹配基线如实留空 | 没有对照就宣称净省时百分比、普遍艺术提升或“原来绝对做不出” |

不要求作者用所有算子。发现缺口可以按公开接口绕开或写自己的实现，同时记录它是艺术扩展、公共能力缺失、误用、契约问题还是 bug。不得由开发者现场透露内部实现来“帮助测评通过”。

## 交付与追踪

每轮至少保留 brief、公开资料读取清单、工具输入输出、自己的版本源码、关键图片、选择记录、验证及导出引用和报告。失败调用也是证据。报告不依赖临时目录才可理解；大体积快照/原始缓冲可放 ignored records，登记稳定归档路径。

原报告保持不变。维护者单独登记发现、修复和回归；原测评构建和修复构建用不同摘要。独立创作者只通过公开调用补测，避免开发者把工程单测当成创作复核。若新功能还没独立闭环，就明确标“创作测评待完成”。完整角色动作、资产冻结、目标引擎导入、性能、独立 MCP 客户端兼容等不得从本轮有限任务推断已经完成。
